# Home Tabs

- The home page uses the `@vigilant-broccoli/react-lib` `Tabs` pattern (as `HomeCalendarTabs` in `local-manager-next`) with icon-only Calendar, Event Calendars, Tasks, Notepad, Quick Links and Weather tabs (each has an `aria-label` and `title`), sized for touch.
- `TabbedView` (from `@vigilant-broccoli/react-lib-higher-level`) is the generic tab shell: a tab list with an optional actions slot, and per-tab `forceMount`. `HomeView` supplies the tabs.
- The active tab is mirrored in the `?tab=` query param (omitted for Calendar), so `/?tab=Tasks` deep-links, and saved in `localStorage` (`vb-manager-mobile-tab`). On load a valid `?tab=` wins; otherwise the stored tab is restored after mount (avoiding a hydration mismatch) and mirrored into `?tab=`, falling back to Calendar. `/task-list` redirects there.
- Tasks renders `GoogleTasksView` with drag and drop disabled, as this is a touch view. It is force-mounted so tasks load with the page, and refetches each time the tab is reopened; refetching the list already shown keeps it on screen (the skeleton appears only on a list's first load). The create-event button is shown on this tab too, alongside its own Create tasks button.
- The page is fixed to the viewport (the document never scrolls). The tab row stays on top and each tab panel fills the rest and scrolls inside itself only when its content overflows; the phone agenda is its own scroll container with a hidden scrollbar, overscroll containment and bottom safe-area padding, and the desktop iframe fills its panel.
- Force-mounted panels fill without scrolling, so Tasks and Notepad wrap their content in the default scrolling, safe-area-padded container.
- The Calendar tab is force-mounted and hidden with `display: none` plus `aria-hidden`, so the Google Calendar iframe is not reloaded when switching tabs.
- Notepad renders `NotepadEditor` inline, force-mounted so its content and realtime sync load with the page and its cursor and scroll position survive tab switches, and Quick Links renders the react-lib-higher-level `QuickLinksPanel` (the body of `QuickLinksDialog`) with browser-local favorites, an integrated star toggle and a top Favorites group; neither has a sidebar entry. Quick Links includes the registry's `Agentic` subgroup, built from the README-derived workflow phases, so mobile and desktop share one list.
- Weather renders the same `WeatherClockCardUtilityContent` card as weather.harryliu.dev (`react-utility`), fed by the auth-guarded `/api/weather` (Open-Meteo plus Nominatim city) route; preparation badges use the shared synchronous `common-js` calculator ([thresholds](../../../ui/weather-next/docs/features/preparation-badges/README.md)). `WeatherView` is loaded with `next/dynamic` (`ssr: false`) so its chunk stays off the critical path, and the tab is force-mounted so the card locates and fetches once on load; switching to Weather is instant.
- Event Calendars is read-only: a list with per-calendar visibility toggles, with no sync, untracked or edit actions. Cards, links, action hover states and loading/empty/error messages follow the active light or dark theme.
- Hidden Google calendar ids are saved in local storage under `vb-manager-hidden-event-calendars`.
- The embed URL, base config, event calendar colors and hidden-id helpers come from `@harry/personal` and are shared with `local-manager-next`.
- The phone agenda (`CalendarAgenda` in `react-lib-higher-level`) draws a red "now" line with a left dot in the Today group, above the first upcoming timed event (below all events when none remain, never above all-day events). The clock refreshes every minute. When events first render with the Calendar tab visible, the agenda's own scroll container instantly scrolls so the line sits about 18% down the area below the sticky Today heading (stuck to the container's top), clamped to the scroll range; later renders, including the minute tick, never re-scroll.
- Tapping an agenda event opens `CalendarEventDetails` (`react-lib-higher-level`), a read-only bottom sheet below `sm` that slides up on open and down on close (skipped under reduced motion; the `sheet-in`/`sheet-out` keyframes live in this app's Tailwind config) and a centered dialog from `sm` up: the calendar's color dot and name, title, date/time (All day or start–end, with the full range for multi-day events, not the per-day agenda copy), a repeating-event hint, a Join button for `hangoutLink`, the location linked to a Google Maps search, attendees with RSVP status and organizer, and the description as plain text (HTML stripped, anchors kept as their URL, `http(s)` URLs linkified; never injected as markup). Sections without data are hidden; the footer opens the event in Google Calendar and pads for the bottom safe-area inset. The fields come from the same `events.list` call (`mapEvent` in `google-workspace`), so no extra requests or scopes. `CalendarAgenda` only renders rows as buttons when given `onEventClick`; otherwise they stay links to Google Calendar, as in the component library's Mobile Home demo.
- The agenda, Event Calendars list and `TabbedView` live in `@vigilant-broccoli/react-lib-higher-level`, which the component library's Mobile Home entry (under its `react-lib-higher-level` group) renders with sample data inside a phone frame with the top bar, sidebar drawer, pinned layout, Create calendar event dialog and task voice input mocked, so UI edits there change the deployed page. `HomeView` keeps the fetching, auth and Google reconnect.
- Calendar event creation uses `CreateCalendarEventDialog` from `react-lib-higher-level`, shared with local-manager; the dialog fills phone screens and centers on desktop while preserving mobile voice input and Google reconnection.
- The Create calendar event dialog is a full-screen sheet below the `sm` breakpoint (`fullScreenOnMobile`, `100dvh`) and a centered 600px dialog from `sm` up. `CalendarInput` renders the layout: a header with the visible title and a Close button, a scrollable body (textarea, images, input buttons, event drafts) and a footer with the Extract events button, padded for the top and bottom safe-area insets. The textarea is auto-focused only on desktop, so the iOS keyboard opens when the user taps it; after a successful parse the textarea is blurred to dismiss the keyboard and the first event draft scrolls into view.
- `agentic-workflows.ts` drops the README's Test phase (the pipeline smoke test) and inserts a hand-written Deploy phase before Maintain (lifecycle order; appended if Maintain is missing) linking `manual-promote-production`, which is not agentic and so is absent from the README table.
- The Agentic data is generated from the root README's `### Agentic` table by `libs/@vigilant-broccoli/manager/scripts/generate-agentic-workflows.ts` into `libs/@vigilant-broccoli/manager/src/lib/generated/agentic-workflows.json` (gitignored). The manager library’s Nx `generate-agentic-workflows` target hashes the README and runs before `build`, `serve`, `serve:no-vault`, `lint` and `typecheck`; run it with `pnpm nx run @vigilant-broccoli/manager:generate-agentic-workflows`. It keeps only the Phase, Description and Actions columns; Docker Sandbox and Local are ignored. The same run writes `workflowNames`: every `.github/workflows/*.yml` whose name starts with `ci-`, `cron-`, `deploy` or `manual-` and that has a `workflow_dispatch` trigger. The target also hashes that directory, and `EXTERNAL_QUICK_LINKS` lists the ones not already in the Agentic group under `Workflows`, so a new or removed workflow file needs no code change.
- The table must keep this format or the build fails with a message naming the problem: the `### Agentic` heading; header columns starting `Phase | Description | Actions`; Description as `` `name` — summary `` (first `—` splits them); Actions as a single markdown link to an `https://` page whose text is the GitHub workflow name (the row's displayed name), or `N/A` to leave the row out (a workflow with no Actions page). Phases and rows keep README order.
- The JSON is generated rather than committed because the Vercel deploy builds on the runner against the full checkout (`vercel build --cwd <repo root>`, see the [Vercel deploy pattern](../../../../../../docs/app-development/ui/deployment/vercel-deploy-pattern.md#the-build-runs-on-the-runner-not-on-vercel)), so the README is always present. Nx cannot hash a file outside the workspace root, so the target hashes the README through a `runtime` input.

- `EXTERNAL_QUICK_LINKS` builds the Agentic group from `AGENTIC_PHASES`, so mobile and desktop Quick Links both pick up README table changes. Both apps generate the data before development, lint and builds.

## Application identity compatibility

- The Nx project and app directory are `mobile-manager-next`; the display name is Mobile Manager Next.
- Deploy targets use the new Nx identity with the existing Vercel projects `staging-vb-manager-next-mobile` and `production-vb-manager-next-mobile`; hosting summaries map the new identity to that provider name.
- `manager.harryliu.dev`, staging/production Vercel URLs, OAuth callbacks and Vercel Authentication remain unchanged; no cloud migration or Terraform apply is needed.
- Terraform retains the `vb-manager-next-mobile` DNS map key because `post-apply.sh` derives `production-<key>` for domain attachment; renaming that key would also change resource addresses.
- Upptime names, slugs and archived `history/` retain the legacy identity to preserve monitoring continuity. Historical SQL migrations also retain their original comments.
- Auth configuration, Google token storage, theme and saved preference keys remain unchanged, so existing sessions and preferences survive on the same origins.
- The local `local-manager-next` dashboard is a separate app.
