# Ansible

Agentless configuration management: a control node SSHes into hosts and runs
idempotent tasks until the host matches the described state. Push-based, needs
no agent on the target — only Python and SSH.

## Free Tier

- `ansible-core` and the community collections are free and open source (GPLv3)
  — no account, no node limit, no telemetry.
- Ansible Galaxy (the public collection/role registry) is free to pull from and
  publish to.
- The paid product is Red Hat Ansible Automation Platform: a web UI, RBAC,
  scheduling, job history, supported collections. Nothing in the CLI workflow
  requires it.

## Concepts

| Term       | Description                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------ |
| Collection | Distributable bundle of modules/roles/plugins (`ansible.posix`, `community.docker`), pinned in a requirements file |
| Fact       | Detail gathered from the host before tasks run (OS family, architecture, mounts), usable in conditions             |
| Handler    | Task that runs only if something notified it, once per play — the "restart the service if config changed" hook     |
| Host Vars  | Variables scoped to a single host, usually `host_vars/<host>.yml`                                                  |
| Group Vars | Variables scoped to an inventory group, usually `group_vars/<group>.yml`                                           |
| Inventory  | The list of hosts and groups, INI or YAML, static or generated by a dynamic inventory plugin                       |
| Module     | The unit of work (`apt`, `file`, `systemd_service`) — declares desired state rather than commands                  |
| Play       | A mapping of one host group to a list of tasks                                                                     |
| Playbook   | A YAML file of plays                                                                                               |
| Role       | A directory convention (`tasks/`, `templates/`, `handlers/`, `defaults/`) for reusable, shareable units            |
| Tag        | Label on a task or import so a run can be narrowed to part of a playbook                                           |
| Vault      | Ansible's own encrypted-file format for secrets kept beside the playbook                                           |

## When to Reach for It

| Situation                                     | Tool                                                                   |
| --------------------------------------------- | ---------------------------------------------------------------------- |
| Cloud resources — instances, disks, DNS, IAM  | Terraform (declarative state of things that must exist)                |
| First boot of a disposable cloud VM           | cloud-init (runs once, per instance)                                   |
| A machine image built ahead of time           | Packer                                                                 |
| Long-lived host that must converge repeatedly | Ansible (re-runnable, and the only one of these that reconciles drift) |

Bare-metal and on-prem hosts are the clearest case: there is no API to create
them, so there is nothing for an infrastructure provisioner to own, and their
lifetime is long enough that "run once at boot" is not good enough.

## Install

```
brew install ansible                  # macOS
pipx install ansible-core             # any platform, CLI only
ansible-galaxy collection install -r requirements.yml
```

## Layout

```
ansible.cfg              # inventory path, SSH behaviour, output callback
inventory/hosts.yml      # hosts and groups
group_vars/<group>.yml   # shared defaults
host_vars/<host>.yml     # per-host values
playbook.yml             # plays, handlers
tasks/*.yml              # task files imported by the playbook
templates/*.j2           # Jinja2 templates rendered onto hosts
```

Host vars override group vars. A playbook can import task files directly
instead of defining roles — roles pay off once something is shared between
playbooks.

## Commands

```
ansible-playbook playbook.yml                    # converge
ansible-playbook playbook.yml --check --diff     # dry run, show what would change
ansible-playbook playbook.yml --tags docker      # only tagged tasks
ansible-playbook playbook.yml --limit host-a     # subset of the inventory
ansible-playbook playbook.yml -e var=value       # extra vars (visible in argv — not for secrets)
ansible all -m ping                              # ad hoc connectivity check
ansible all -m setup                             # dump gathered facts
ansible-inventory --host <host>                  # resolved vars for one host
ansible-lint playbook.yml                        # style and correctness lint
```

## Idempotency

The property that makes a playbook safe to re-run: a second run should report
`changed=0`. It comes from using modules that declare state rather than
shelling out.

- Prefer a module over `command`/`shell`. When a shell-out is unavoidable, pair
  it with a `creates:`/`removes:` guard or an explicit `changed_when:` derived
  from the command's own output.
- `register` a check command with `changed_when: false`, then gate the real
  action on its result.
- Put service restarts in handlers, so a converged run doesn't bounce anything.
- Never template a file to a path the service also writes to; the run will
  fight the service and report a change every time.
- Secrets passed as `-e` land in the control node's process arguments. An
  environment variable read via `lookup('env', ...)`, or a file staged on tmpfs
  and referenced by path, keeps them out of `ps`.
