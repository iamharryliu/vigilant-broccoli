# Audit: Cloud Deployment Statefulness

> Deployed app/service inventory reviewed for reliance on local disk/in-memory state vs. externalized cloud-managed state · 2026-08-23

## Scope

Every deployed cloud app/service in the repo (Fly.io services under `apps/api/*`, Cloudflare Pages/GitHub Pages static sites, Vercel Next.js apps, the Sanity CMS, and the two Docker-Hub/VM-hosted socket servers plus the PM2-on-VM `vb-manager-next`) was checked for local SQLite/disk usage, Fly volume mounts, and in-process/in-memory state (websocket room registries, caches) that isn't backed by a managed external store (Postgres/Supabase, GCS/R2, etc.).

## Findings

| #   | Severity | Location | Finding | Remediation |
| --- | -------- | -------- | ------- | ----------- |
| 1   | High     | `projects/nx-workspace/apps/api/vb-express/src/auth.ts:3,14-15`, `projects/nx-workspace/deployment-configs/fly-configs/{staging,production}-vb-express.toml:12,15-16` | **STATEFUL.** better-auth (sessions, OAuth tokens, API keys) is persisted via `node:sqlite` `DatabaseSync` to `DATABASE_PATH=/data/vb-express.sqlite`, backed by a Fly persistent volume (`[mounts] source = 'vb_express_data'`). Auth data lives on a single-machine local disk, not a managed DB — the service cannot scale beyond 1 Fly machine without a migration. | Migrate auth storage to a managed Postgres (e.g. Supabase, already used elsewhere in the repo) if multi-machine scaling or volume-loss resilience is ever needed; otherwise document this as an accepted single-instance constraint. |
| 2   | High     | `projects/nx-workspace/apps/socket-server-socketio/src/main.ts:98,140` | **STATEFUL.** Socket.IO server uses the default in-process room adapter (`socket.join(room)`, `io.sockets.adapter.rooms`) with no Redis (or other) adapter configured. All room/connection membership lives only in this one Node process's memory; it is pinned to a single VM/container by necessity, not just by current deployment choice. | If horizontal scaling of this service is ever needed, add `@socket.io/redis-adapter` backed by a managed Redis. Otherwise no action needed as long as it stays single-instance. |
| 3   | Medium   | `libs/@vigilant-broccoli/slackbots/src/office-presence-app/utils/db.utils.ts:14` | **STATEFUL.** `better-sqlite3` opens a relative-path file `new Database('state.db')` storing `user_presences`/`office_events`/`user_settings`. No `-v`/volume flag was found in this repo's tracked run commands (`README.md` `docker run` examples, `serve:docker` nx target) for `office-presence-socket-server-demo`, so as configured in-repo the DB lives in the container's writable layer and is lost on every container replace/redeploy unless an operator manually adds an untracked bind mount. | Confirm operationally whether a bind mount/volume is attached outside of tracked config; if not, add one (or externalize to a managed DB) so presence history survives redeploys. |
| 4   | Info     | `projects/nx-workspace/apps/ui/vb-manager-next/ecosystem.config.js` (`instances: 1`) | **STATEFUL by design, not a defect.** Core app data is Supabase-backed, but several API routes (`src/app/api/docker/containers/route.ts`, `src/app/api/network-monitor/*`, `src/app/api/local-services/route.ts`, `src/app/api/wrangler/pages/route.ts`) intentionally introspect the host VM's Docker daemon/LAN/local processes. The app is a single-VM home-server dashboard by nature; single-instance PM2 config matches that intent. | None — flagged for completeness only. |
| 5   | Info     | `projects/nx-workspace/apps/whiteboard`, `projects/nx-workspace/apps/vb-manager-next-mobile/src/app/api/notepad/route.ts` | **Not stateful.** The two Yjs/CRDT features (whiteboard, and the recent notepad live-sync in commit `e13ad2a27`) keep the Y.Doc entirely client-side and relay updates via Supabase Realtime Broadcast (a managed service); durable snapshots go through `supabaseAdmin.from('notepad')` Postgres CAS. No server process in this repo holds room state for these features, so they introduce no scaling hazard despite being CRDT-based. | None. |

All other deployed apps — `llm-service`, `bucket-service`, `email-service`, `email-subscription-service` (Fly.io); `cloud-8-skate-angular`, `docs-md`, `journal`, `personal-website-react`, `pages-index`, `component-library` (Cloudflare/GitHub Pages, static); `hearth`, `findme`, `employee-handler-ui` (Vercel); `cloud8skate-sanity` (Sanity) — externalize all state to managed cloud services (Supabase/Postgres, GCS/R2, RabbitMQ, CDN edge) or hold no state, and show no locally/in-process-only persistence.

## Recommendations

1. Highest priority: decide whether `vb-express`'s auth SQLite-on-volume (#1) is an accepted constraint or needs migrating to managed Postgres — it's the only service holding security-sensitive state (sessions/OAuth/API keys) locally.
2. Confirm `office-presence-socket-server-demo`'s `state.db` persistence operationally (#3) — silent data loss on redeploy is easy to miss since it isn't visible from tracked config alone.
3. `socket-server-socketio` (#2) and `vb-manager-next` (#4) are fine as-is provided both stay single-instance; no action needed unless scaling requirements change.
