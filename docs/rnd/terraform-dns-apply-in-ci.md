# R&D: Applying only Cloudflare DNS Terraform from CI after production deploys

> Can GitHub CI apply just the Cloudflare DNS part of the Terraform config, so a new production app's domain is wired up automatically after it deploys? · 2026-10-07

## Context

Yes, but the current layout makes it unsafe as-is. All infrastructure is one root module in one Terraform Cloud workspace (`infrastructure/terraform/main.tf:5`) holding Google, OCI, AWS, GitHub, Supabase and Cloudflare. Applies are local only (`docs/ci/terraform.md`), and the only CI identity is the read-only drift SA (`infrastructure/terraform/github-actions-tf-drift.tf`). DNS is 20 `cloudflare_dns_record`s across `cloudflare-*.tf`, and most are static CNAMEs to Pages, Vercel or Fly (`cloudflare-vercel-apps.tf:14`, `cloudflare-harryliu-dev.tf:75`). A few point at other managed resources, such as the tunnel CNAME in `cloudflare-vault.tf:42`.

## Alternatives

| Option                                                          | Pros                                                                                                                                                                                                    | Cons                                                                                                                                                                                                                                                                                                                                                                               | Cost                                                                                                                             | Security                                                                                                                                                                                                                                                              | Scalability                                                                                                                       |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **A — `terraform apply -target=cloudflare_dns_record.…` in CI** | No restructuring. The drift workflow already proves CI can `init` and plan this config (`.github/workflows/cron-terraform-drift.yml`)                                                                   | HashiCorp documents `-target` as an exception, not routine use. CI still needs every provider credential, including OCI config and AWS keys, because the whole config is loaded. A target list must be kept in sync by hand. Untargeted drift piles up silently                                                                                                                   | Free                                                                                                                             | Poor. Write access to the whole workspace state (`TF_CLOUD_TOKEN` is org-wide), and a full-zone `CLOUDFLARE_API_TOKEN`. Any bug in the workflow can modify GCP IAM or VMs                                                                                            | Degrades as the target list grows                                                                                                 |
| **B — Split DNS into its own root module and TFC workspace**    | Real isolation: CI loads only the `cloudflare` provider and only DNS state. A plan cannot touch anything else. Fits the existing "Terraform owns DNS" rule and drift detection                           | One-time migration: `removed` blocks in the old root plus `import` blocks in the new one (or `terraform state mv` between workspaces). Records that point at other resources (tunnel ids, OCI IPs) must stay in the main root or read values through `tfe_outputs` / `terraform_remote_state`. Needs a new Cloudflare token with only `Zone:DNS:Edit` (plus `Pages:Edit` if `cloudflare_pages_domain` moves too), stored in Vault. The workflow gets a WIF provider and Vault role pinned to its `job_workflow_ref` on `main`, following the `github-tf-drift` pattern. No new GitHub repo secret | Good. Adding an app means adding a map entry                                                                                      |
| **C — Deploy script upserts DNS through the Cloudflare API**    | Simplest runtime path, mirroring `scripts/vercel-domains.ts` called from `post-apply.sh:323`. Runs inline in `deploy.yml` with no Terraform                                                              | Breaks "Terraform owns DNS" (`infrastructure/terraform/CONTEXT.md`). Records created this way are invisible to state and to `cron-terraform-drift`, or fight Terraform if they are also declared there                                                                                                                                                                              | Free                                                                                                                             | Same DNS-only token as B, but it sits in the general deploy job's environment                                                                                                                                                                                         | Poor. Two sources of truth for one zone                                                                                           |
| **D — Keep applies local and have the deploy check DNS**        | No new credentials in CI                                                                                                                                                                                | Doesn't automate anything. It only shortens the feedback loop, using the same kind of check as the existing `flyctl certs show` step (`.github/workflows/deploy.yml:267`)                                                                                                                                                                                                         | Free                                                                                                                             | Best: nothing changes                                                                                                                                                                                                                                                 | Unchanged manual step per app                                                                                                     |

## Recommendation

**B — split DNS into its own root module and TFC workspace.** Moving the static CNAMEs into their own workspace is the only option that limits what a CI apply can reach. CI would hold a DNS-only Cloudflare token and DNS-only state, so a workflow bug cannot reach VMs, IAM or secrets, and drift detection still covers every record. **A** is the runner-up. It wins only for an occasional, manually dispatched apply where restructuring isn't worth it, and even then it should run under `environment:` approval rather than right after deploy.

## Sample Implementation

1. Create `infrastructure/terraform/dns/` with its own `cloud { workspaces { name = "vigilant-broccoli-dns" } }` block and only the `cloudflare` provider. Move the static records there: the `vercel_app_subdomains` map from `cloudflare-vercel-apps.tf` and the Pages CNAMEs from `cloudflare-{docs,links,utilities,…}.tf`. Leave tunnel- and IP-backed records in the main root.
2. Migrate state without destroying anything. Add `removed { from = cloudflare_dns_record.vercel_app  lifecycle { destroy = false } }` in the old root and `import { to = cloudflare_dns_record.vercel_app["findme"] id = "<zone_id>/<record_id>" }` in the new one. Then run `pnpm tf:plan` against each root and confirm the result is no-op.
3. Add a Cloudflare API token scoped to `Zone:DNS:Edit` on `harryliu.dev`, stored in Vault `kv/data/secrets` and listed in `docs/infrastructure/secret-management.md`.
4. Mirror `github-actions-tf-drift.tf` with a WIF provider and SA, and a Vault JWT role (the `role` input of `.github/actions/vault-secrets/action.yml`). Pin each one to `.github/workflows/deploy-dns.yml@refs/heads/main`.
5. Add the workflow and trigger it after production deploys:

```yaml
# .github/workflows/deploy-dns.yml
on:
  workflow_run:
    workflows: [deploy]
    types: [completed]
    branches: [production]
  workflow_dispatch:
jobs:
  apply-dns:
    if: github.event_name == 'workflow_dispatch' || github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    concurrency: { group: deploy-dns, cancel-in-progress: false }
    steps:
      # checkout + vault-secrets (TF_CLOUD_TOKEN, CLOUDFLARE_DNS_API_TOKEN → CLOUDFLARE_API_TOKEN)
      - working-directory: infrastructure/terraform/dns
        run: |
          terraform init -input=false
          terraform apply -input=false -auto-approve > /dev/null   # public repo: never print the plan body
```

6. Extend `cron-terraform-drift.yml` with a matrix entry for `infrastructure/terraform/dns`. Update `docs/ci/terraform.md`, since applies would no longer be "local only" for DNS, and add the Upptime/pages-index entries for each new domain as usual.
